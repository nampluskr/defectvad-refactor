## 회차 1 — Critical: 학습 중 validation이 미보정 score를 사용

- 위치: `src/tasks/anomaly/adapters/efficientad.py` (수정 전 `on_fit_end`)
- 지적: 분위수 calibration이 `on_fit_end`에서 전체 학습 종료 후 한 번만 수행된다. `upstream/efficient_ad/torch_model.py#compute_maps`는 `is_set(self.quantiles)`일 때만 정규화하므로, 학습 중 모든 epoch의 validation이 `amax(0.5 * raw_map_st + 0.5 * raw_map_stae)`로 채점된다. 스케일이 다른 두 map을 정규화 없이 합산한 값이며 보정 후 score의 단조 변환이 아니므로, `core/engine.py`가 그 metric으로 선택하는 `best.pth`가 최종 평가와 다른 score 정의로 결정된다. anomalib `lightning_model.py`는 `on_validation_start`에서 매 validation 직전 재계산한다.
- 재현 조건: 모델 생성 → `on_fit_start()` → 1 epoch 학습 → `on_fit_end()` 전에 `eval_step()` 호출 → `model.is_set(model.quantiles)`가 거짓임을 확인. calibration 설치 후 재호출하면 score와 순위가 달라진다.
- 위반: SPEC §4.3 lifecycle/calibration 순서, SPEC §4.5 anomalib 동등성, PRD §5.4 score normalization·post-processing·evaluation protocol.
- **레거시 대조**: 사용자 요청으로 `/mnt/d/archive/_inbox/github/defectvad`를 확인한 결과, 레거시 구현은 이 문제를 겪지 않았다. `common/base_trainer.py#fit`이 매 epoch validation 직전 `on_validation_epoch_start()`를 호출하고 `models/efficientad/model_trainer.py`가 이를 override해 `map_norm_quantiles()`를 재계산한다. 즉 레거시에 있던 올바른 lifecycle hook이 리팩터링 과정에서 누락된 회귀다. `PLAN.md` 55행도 EfficientAD 요건을 "검증 전 분위수 계산"으로 이미 정확히 기술하고 있어, 설계 의도가 아니라 구현이 이탈한 것으로 판정했다.
- 처리: **수정 완료.** `TaskAdapter`에 task-agnostic hook `on_validation_start(model, loaders, device)`를 추가(기본 no-op)하고, `core/engine.py#Trainer.fit`이 루프 안에서 각 epoch의 validation 직전에 호출하도록 했다. `EfficientAdAdapter`가 이를 override해 분위수를 재계산한다. 나머지 4개 task와 `StfpmAdapter`는 기본 no-op을 상속하며 모델명 분기는 도입하지 않았다(NFR-005).

### 회차 1 Minor — calibration 입력이 비었을 때 불투명하게 실패

- 위치: `src/tasks/anomaly/adapters/efficientad.py#_map_norm_quantiles`, `#_quantiles_of_maps`
- 지적: `label == 0` 샘플만 수집하면서 빈 리스트를 검사하지 않아 `torch.cat([])`가 불투명한 오류를 낸다. `qb > qa` 보장도 없어 map이 붕괴하면 `torch_model.py:692`에서 0으로 나눠 비유한 score가 나온다.
- 위반: SPEC §4.3 calibration 계약, PRD §5.4.
- 처리: **수정 완료.** 정상 샘플 부재 시 `LocalAssetError`로 원인과 확인할 config 키를 함께 알리고, `qa`/`qb`의 유한성과 `qb - qa > 0`을 검사해 붕괴한 보정을 거부한다. `upstream/`은 수정하지 않고 호출 측에 두었다(CON-001).

## 회차 2 — Critical: `on_fit_end` 재보정이 선택 metric과의 짝을 깨뜨림

- 위치: `src/tasks/anomaly/adapters/efficientad.py#on_fit_end`
- 지적: 1차 수정으로 매 epoch 보정이 추가된 뒤에도 `on_fit_end`가 무조건 재보정한다. 분위수는 `nn.Parameter`이므로 `best.pth`의 `model_state`에 함께 저장되고 `core/engine.py`가 `on_fit_end` 직전에 이를 복원한다. 즉 재로드 시점에 이미 올바른 짝이 복원되는데, 재보정하면 `reduce_tensor_elems`가 2^24 원소 초과 시 `torch.randperm`으로 새 표본을 뽑아 다른 분위수로 교체한다. 저장되는 모델이 그것을 선택한 `best_metric`과 다른 score 정의를 갖게 된다.
- 재현 조건: 정상 valid map 집합이 2^24 원소를 초과 → 매 epoch 보정으로 `best.pth` 저장 → 재로드 후 `on_fit_end`가 새 난수 부분집합으로 재보정 → `model_state`만 덮어써지고 `best_metric`은 이전 분위수 기준 값으로 남음.
- 위반: SPEC §4.3, SPEC §4.5, PRD §5.4.
- **유효성 검토**: 지적은 코드상 타당하나 현재 설정에서는 발동하지 않는 잠재 결함으로 판정했다. `reduce_tensor_elems`의 랜덤 샘플링은 원소 수 > 2^24(16,777,216)에서만 발동하는데, 실제 정상 valid 이미지는 bottle 8·carpet 11·capsule 9장으로 256×256 기준 0.52M~0.72M 원소(임계값의 약 4%)다. 256×256에서 발동하려면 정상 valid 이미지가 256장 이상이어야 한다. 스모크 실행에서도 best epoch(1)의 `image_auroc=0.9950000047683716`/`pixel_auroc=0.8150076270103455`와 재보정 후 최종 평가값이 비트 단위로 동일해, 현재 스케일에서 재보정이 결정론적으로 같은 값을 재현함을 실증했다. 따라서 이번 P5 실행 결과에는 영향이 없다. 심각도는 Critical보다 Major에 가깝다고 판단하나, 수정이 간단하고 이후 image_size·split 확대 시 실제 결함이 되므로 그대로 반영했다.
- 처리: **수정 완료.** `on_fit_end`는 `model.is_set(model.quantiles)`가 거짓일 때만 보정한다. `train.epochs=0`처럼 루프 내 `on_validation_start`가 한 번도 실행되지 않은 경우에만 해당하며, 그 외에는 `best.pth`가 복원한 가중치·분위수 짝을 그대로 신뢰한다. `compute_thresholds`가 미보정 모델을 보는 경우는 남지 않는다.

### 회차 2 Minor — calibration이 다음 epoch의 학습 RNG를 교란

- 위치: `src/tasks/anomaly/adapters/efficientad.py#_calibrate_quantiles`
- 지적: `reduce_tensor_elems`가 map이 놓인 device의 전역 RNG를 소비하므로, valid split의 정상 이미지 수가 다음 epoch의 autoencoder dropout 순서와 sampler 순서를 바꾼다.
- 위반: SPEC §4.3, SPEC §4.5, PRD §5.4, AC-009.
- 처리: **수정 완료.** calibration 패스를 `torch.random.fork_rng(devices=[device] if cuda else [])`로 감쌌다. CUDA에서 RNG 상태가 보존됨을 직접 확인했고(`torch.equal(before, after) == True`), `upstream/`은 수정하지 않았다(CON-001).

## 회차 3 — 최종 재검토 결과

**Critical/Major/Minor 지적 0건.** 이전 지적 판정은 다음과 같다.

- 회차 1 Critical: **RESOLVED.** 실행되는 모든 epoch이 학습 후·validation 전에 `on_validation_start`를 호출하므로, epoch `e`는 같은 가중치 `W_e`로 보정한 분위수로 채점된다.
- 회차 2 Critical: **RESOLVED.** `best.pth`가 선택된 가중치와 그 분위수를 함께 복원한 뒤 `is_set`이 참이므로 `on_fit_end`가 재보정하지 않는다. threshold 계산과 최종 평가가 선택된 `W_best/Q_best` 짝을 쓰고, 최종 재저장도 그 짝을 보존한다.
- 회차 2 Minor: **RESOLVED.** `fork_rng`가 프로세스 CPU generator와 활성 CUDA device generator를 예외 상황 포함해 스냅샷·복원한다.

검토자가 `Trainer.fit`의 9개 경로(`checkpoint_dir` 설정/미설정, `train.epochs=0`의 기존 best 유무, 개선 epoch 부재, resume, 최종 재저장)를 전수 추적해 모든 경로에서 `compute_thresholds` 시점과 최종 평가 시점의 분위수가 채점 대상 가중치와 정확히 짝을 이룸을 확인했다.

`is_set` false-negative 가능성도 확인했다. 분위수는 4개 스칼라 0.0으로 초기화되고 `is_set`은 각 값을 개별 검사하므로 상쇄가 없다. map이 제곱 거리라 음수가 아니고 새 guard가 두 branch 모두에서 `qb > qa`를 강제하므로, 보정에 성공한 dictionary가 네 값 모두 0이 되는 경우는 없다. 다만 `is_set`은 존재 검사이지 출처 검사가 아니므로, 외부에서 손상·부분 복원된 state에 대해서는 참을 반환할 수 있다 — 추적한 `Trainer.fit` 경로 안에서는 checkpoint 복원이 원자적이고 가중치가 바뀌는 모든 epoch이 채점 전 재보정하므로 해당 경로가 없다.

`fork_rng`의 한계도 기록한다. 독립 `torch.Generator` 객체와 DataLoader worker 프로세스 내부 RNG는 스냅샷하지 않는다. `reduce_tensor_elems`발 누수와는 무관하고 valid worker가 메인 프로세스 전역 generator를 바꾸지 않으므로 이번 지적 범위에서는 문제되지 않는다.

## 수정 후 재측정 결과 (P5-T02)

사용자가 수정 후 코드로 3개 카테고리를 동일 조건(`epochs=20`, `batch_size=1`, 256×256)으로 재실행한 결과다.

### 수정 효과 검증 — 최종값과 epoch별 값의 일치

수정 전 실행에서는 최종 보고값이 20개 epoch 중 어느 값과도 일치하지 않았다. 수정 후에는 세 카테고리 모두 정확히 일치한다. epoch별 검증과 최종 평가가 서로 다른 score 정의를 쓰고 있었다는 직접 증거이며, 회차 1 Critical이 실제 실행에서 해소되었음을 확인한다.

| 카테고리 | 수정 전 최종값이 epoch에 존재 | 수정 후 | 선택된 epoch |
|---|---|---|---|
| capsule | 아니오 (0.6164 부재) | 예 | 8 |
| carpet | 아니오 (0.9318 부재) | 예 | 6 |
| bottle | 아니오 (pixel 0.9221 부재) | 예 | 3 |

### 성능 비교

| 카테고리 | image AUROC (전 → 후) | pixel AUROC (전 → 후) | reference |
|---|---|---|---|
| capsule | 0.616 → 0.683 (+0.067) | 0.909 → 0.944 (+0.035) | 0.982 |
| carpet | 0.932 → 0.977 (+0.045) | 0.958 → 0.957 (±0) | 0.982 |
| bottle | 1.000 → 1.000 (동일) | 0.922 → 0.922 (동일) | 0.982 |

bottle이 동일한 이유는 두 실행 모두 epoch 3을 선택했고, 최종 평가는 원래부터 보정된 상태로 계산되었기 때문이다.

### capsule 잔여 gap 원인 진단

capsule이 reference와 여전히 큰 차이를 보여, image score 집계 방식이 원인인지 저장된 `best.pth`로 평가만 수행해 진단했다(제품 코드 미변경, 진단 스크립트는 scratchpad에만 존재).

| 집계 방식 | capsule | carpet | bottle |
|---|---|---|---|
| amax_raw (현재, upstream `forward()` 그대로) | 0.6825 | 0.9773 | 1.0000 |
| amax_smoothed | 0.5979 | 0.9801 | 1.0000 |
| top 0.1% 평균 | 0.6402 | 0.9744 | 1.0000 |
| top 1% 평균 | 0.6085 | 0.9517 | 1.0000 |
| 전체 평균 | 0.4709 | 0.5057 | 0.9850 |

현재 방식이 이미 최선이며 어떤 대안도 capsule을 구제하지 못한다. 따라서 잔여 gap은 집계·후처리가 아니라 학습된 표현 자체에 있다. PRD §5.4의 post-processing·metric 항목은 원인에서 배제한다. 남은 요인은 두 가지다.

- **학습 예산**: 카테고리당 4,380~5,600 스텝으로, anomalib이 reference를 산출한 70,000 스텝의 약 6~8%다.
- **추정 분산**: capsule valid의 정상 이미지가 9장뿐이다. 정상 1장의 순위 이동만으로 AUROC가 최대 `42/378 = 0.111` 움직인다. 관측된 0.32~0.68 진동은 정상 3장 분량의 순위 변동에 해당하므로 상당 부분이 모델 불안정이 아니라 추정 잡음이며, 그 상태에서 epoch별 최댓값으로 best를 고르는 것은 valid split에 대한 과적합에 가깝다.

재측정에서 새로 드러난 결함이다. **수정하지 않았으며 후속 결정이 필요하다.**

- 위치: `src/core/engine.py#Trainer.fit`의 `improved` 판정
- 내용: 갱신 조건이 엄격한 부등호(`current > best_metric`)이므로 monitor metric이 상한에 도달하면 이후 갱신이 없다. bottle은 `image_auroc`가 epoch 3에 1.0에 도달해 `best.pth`가 거기서 고정되는데, `pixel_auroc`는 계속 개선되어 epoch 20에 0.985에 이른다. 보고된 bottle pixel_auroc 0.922는 모델 성능이 아니라 선택 정책의 산물이며 실제 도달값보다 0.063 낮다.
- 영향 범위: `core/`의 공통 선택 정책이므로 anomaly 외 4개 task에도 동일하게 적용된다. 등급 C(계약 변경)에 해당해 사용자 승인 없이 진행하지 않는다.
- 고려 가능한 방향: monitor metric을 포화하지 않는 지표로 바꾸기, 동점 시 후순위 epoch을 채택하기, 복합 지표 사용. 어느 쪽도 모델명 분기 없이 공통 루프에서 해결해야 한다.

## 남은 위험

- capsule은 수정 후에도 image AUROC 0.683으로 reference 0.982와 차이가 크다. 위 진단에 따라 구현 결함이 아니라 학습 예산과 검증 세트 크기 문제로 판정하나, 이 판정은 예산을 늘린 실행으로만 최종 확인된다.
- 학습 예산(`epochs=20`)은 P4-T04에서 동작 확인용으로 정한 값으로 anomalib reference 산출 조건과 다르다. reference와의 정량 비교에는 이 차이가 남아 있다.
- monitor metric 포화 문제(위)가 미해결이다.
- `P5-T03`(AC-001~AC-010 전수 검증)은 미수행이며 P5 phase는 완료되지 않았다.

## 결론

Critical 2건(회차 1·2)과 Minor 2건 모두 수정하고, 3회차 재검토에서 전 항목 RESOLVED·신규 지적 0건을 확인했다. 수정 후 재측정에서 최종값과 epoch별 값의 일치를 세 카테고리 모두에서 확인해 결함 해소를 실증했고, carpet(+0.045)·capsule(+0.067)에서 image AUROC 실질 개선을 얻었다.

`P5-T01`·`P5-T02` 완료. `P5-T03`과 P5 phase 완료 판정은 남아 있으며, 그 전에 monitor metric 포화 문제에 대한 사용자 결정이 필요하다.
