## 1차 검토 — 지적 및 처리

### Critical

| # | 지적 | 재현 조건 | 위반 조항 | 처리 |
|---|---|---|---|---|
| 1 | `upstream/` 하위 6개 `__init__.py`가 anomalib 원본(비어있지 않음) 대신 0바이트 파일로 반입됨 | `wc -c`로 6개 파일이 0바이트임을 확인, anomalib v2.3.0 원본과 대조 | CON-001 | **수정** — 6개 파일 모두 삭제. anomalib `stfpm/__init__.py`·`efficient_ad/__init__.py`는 `from .lightning_model import ...`를 포함해 원본 그대로 복사하면 Lightning이 딸려 들어오고(CON-002), `components/__init__.py`도 동일 문제(SPEC §3 기존 결정). `data/dataclasses/torch/__init__.py`는 미반입 서브모듈(`depth`, `image`, `video`)을 import해 ImportError가 난다. 따라서 원본 그대로도, 빈 파일로도 CON-001을 만족시킬 수 없어 __init__.py 자체를 두지 않고 Python 네임스페이스 패키지(PEP 420)로 대체했다. 모든 import는 이미 완전한 모듈 경로(`from src.tasks.anomaly.upstream.stfpm.torch_model import ...`)를 쓰므로 패키지 `__init__`의 재수출 기능이 필요 없다. |
| 2 | 공통 `AnomalyAdapter`로 STFPM/EfficientAD를 학습할 수 없음 (`train_step`이 `NotImplementedError`) | `configs/anomaly/stfpm.yaml`/`efficientad.yaml`을 조립해 첫 배치를 학습 시도하면 예외 | (검토자 제시 기준; SPEC 조항 아님) | **반박 — P1 범위 아님.** `StfpmAdapter`/`EfficientAdAdapter`가 `train_step`을 override하는 것은 SPEC §4.3에 설계돼 있고 `backlog.json`의 P2-T01·P4-T01이 담당한다. P1의 `exit_criteria`는 STFPM/EfficientAD의 실제 학습을 요구하지 않으며, `custom_ae`만 공통 adapter로 동작하면 된다(P1-T02 검증 항목). 2차 검토에서 NOT APPLICABLE로 확인됨. |
| 3 | `eval_step`/`predict_step`이 `outputs["anomaly_map"]`처럼 dict로 접근하지만 upstream 모델은 `InferenceBatch`(NamedTuple)를 반환 | upstream 모델을 `eval_step`/`predict_step`에 직접 통과 | (검토자 제시 기준; SPEC 조항 아님) | **반박 — P1 범위 아님.** SPEC §4.2 "forward 호출과 출력 변환은 모델별 adapter가 담당, anomalib 출력 → `{pred_score, anomaly_map}`"이 P2/P4에서 구현될 계약이다. 2차 검토에서 NOT APPLICABLE로 확인됨. |

### Major

| # | 지적 | 위반 조항 | 처리 |
|---|---|---|---|
| 4 | `resolve_paths()`가 CLI/env/local.yaml이 모두 없으면 config 기본값(`/mnt/d/...`)으로 조용히 성공 | (검토자는 CON-004/silent fallback으로 제기) | **반박, 이후 재확인으로 RESOLVED 판정.** SPEC §6.2 rank-4는 설계된 동작이며 `config["paths"]["_source"]`에 출처가 항상 기록되고(NFR-002), 경로가 실제로 없으면 어느 rank든 `ConfigError`로 실패한다. 2차 검토에서 "silent fallback 아님, NFR-002·CON-004 위반 아님"으로 확인됨. |
| 5 | `classification/custom_cnn.yaml`처럼 `backbone_root`를 쓰지 않는 config도 해당 root 존재를 강제당함 | NFR-003 | **수정** — `used_placeholder_keys()`를 추가해 config 안에서 실제로 `${paths.<key>}`로 참조되는 키만 필수로 검증하도록 변경. |
| 6 | `os.path.isdir(value)` 호출 전 타입 검사가 없어 `--set paths.dataset_root=null` 등이 `TypeError`로 새어나감 | (검토자 제시 기준) | **수정** — `isinstance(value, str)` 검사를 `os.path.isdir()` 호출보다 먼저 추가. |
| 7 | `check-assets`에 `--set`이 없어 CLI 우선순위가 이 커맨드에서만 동작하지 않음 | SPEC §6.2/§6.4 | **수정** — `cli/parser.py`에 `--set` 추가, `check_assets()`가 `apply_overrides()` → `resolve_paths()` → `interpolate()` 순으로 호출하도록 변경. |

## 2차 검토 — 수정 확인

| # | 대상 | 판정 | 근거 |
|---|---|---|---|
| 1 | __init__.py 삭제 | RESOLVED | `upstream/` 하위 `__init__.py` 없음 확인, 남은 9개 파일은 fully-qualified import만 사용, CON-001 문제 해소 |

| 4 | `check-assets --set` | RESOLVED | `--set` 추가, `apply_overrides → resolve_paths → interpolate` 순서로 CLI가 env/local.yaml보다 우선함 확인 |
| 5 | rank-4 기본값 | RESOLVED | 문서화된 rank-4이며 `_source` 기록·실패 시 `ConfigError`로 NFR-002/CON-004 위반 아님 |
| 6 | STFPM/EfficientAD 미동작 | NOT APPLICABLE | P1 exit criteria와 P2-T01/P4-T01 범위 경계상 P1 차단 사유 아님 |
