## 회차 1 — Codex 지적 4건(Major)과 판정

### Major 1 — DFM/DFKDE optimizer가 frozen 파라미터 규칙을 위반, AMP에서 `GradScaler`가 실패할 수 있음

- 위치: `dfm/__init__.py`, `dfkde/__init__.py`, `src/core/builders.py#build_optimizer`, `src/core/engine.py#_train_epoch`
- 지적: 두 factory 모두 backbone을 `requires_grad=True`로 남겨 `build_optimizer`가 backbone 전체를 optimizer에 포함시킨다. adapter의 loss는 모델 파라미터와 연결되지 않은 detached leaf tensor라 모든 파라미터의 `.grad`가 항상 `None`이다. `runtime.amp=true`에서 `GradScaler.step()`이 "No inf checks were recorded for this optimizer"로 중단될 수 있다.
- 판정: **타당하나 신규 결함 아님.** PatchCore·PaDiM이 이미 동일한 패턴을 갖고 있다 — 둘 다 학습 대상이 backbone 외에 전혀 없어, freeze하면 `build_optimizer`가 빈 파라미터 목록을 받아 즉시 `ValueError`가 난다(CFA와 달리 대체할 descriptor 같은 학습 대상이 없다). 이 프로젝트 6개 기존 모델부터 이어진 설계이며 기본 config가 `amp: false`라 드러나지 않는다.
- 처리: **수정 안 함.** DFM/DFKDE만 몰래 다르게 고치면 PatchCore·PaDiM과의 일관성이 깨진다. `docs/dev/v0.2/reports/UPSTREAM-INVENTORY.md` §14에 4개 모델 공통 이슈로 기록하고, 실제 해결에는 `core/builders.py`에 no-op optimizer 전용 경로를 추가하는 등의 공통 코드 변경이 필요하므로 별도 과제로 이월했다.

### Major 2 — 세 factory 모두 `weights_path=None`이면 조용히 random-init backbone 반환

- 위치: `dfm/__init__.py`, `dfkde/__init__.py`, `cfa/__init__.py`
- 지적: `weights_path is not None`일 때만 가중치 검증을 수행하므로, `None`이면 아무 오류 없이 랜덤 초기화된 backbone으로 실행이 진행된다. CON-003/004가 요구하는 "로컬 경로 부재 시 즉시 실패"를 factory 계층이 강제하지 않는다.
- 판정: **타당하나 신규 결함 아님.** STFPM부터 Reverse Distillation까지 기존 6개 모델 전부 동일한 패턴이다.
- 처리: **수정 안 함.** 9개 모델에 걸친 기존 설계라 이번 세션 범위를 벗어난다. `UPSTREAM-INVENTORY.md` §14에 기록.

### Major 3 — CFA `model.params`와 `adapter.params`에 하이퍼파라미터가 중복 선언됨

- 위치: `configs/anomaly/models/cfa.yaml`, `src/tasks/anomaly/adapters/cfa.py`
- 지적: `num_nearest_neighbors`·`num_hard_negative_features`·`radius`가 model과 adapter 양쪽에 독립적으로 존재해, 한쪽만 override하면 `CfaModel`(anomaly map)과 `CfaLoss`(학습 손실)가 서로 다른 하이퍼파라미터를 쓰게 된다. anomalib `Cfa.__init__`은 한 인자 집합을 양쪽에 전달하므로 이 불일치가 원천적으로 불가능하다.
- 판정: **타당함. CFA 신규 코드 고유의 결함.**
- 처리: **수정 완료.** `CfaAdapter.on_fit_start`가 이미 생성된 `model` 인스턴스에서 `model.num_nearest_neighbors`·`model.num_hard_negative_features`·`model.radius`를 직접 읽어 `CfaLoss`를 구성하도록 변경했다. `cfa.yaml`의 `adapter.params`에서 세 값을 제거해 `model.params`가 유일한 출처가 됐다. `num_nearest_neighbors=5`로 모델을 만들면 `adapter.cfa_loss.num_nearest_neighbors`도 자동으로 5가 되는 것을 실측 확인했다(`docs/dev/v0.2/reports/UPSTREAM-INVENTORY.md` §12.5).

### Major 4 — CFA의 전역 `torchvision.models.<backbone>` monkeypatch가 스레드 세이프하지 않음

- 위치: `cfa/__init__.py#build_cfa`
- 지적: lock 없이 전역 모듈 속성을 교체·복원하므로, 여러 스레드가 동시에 `build_cfa`를 호출하면 원본 constructor 복원이 뒤섞여 다른 스레드가 `pretrained=True` 경로(실제 다운로드)로 빠질 수 있다.
- 판정: **타당하나 실제 위험 낮음.** 이 프로젝트의 CLI는 모델을 항상 직렬로 생성한다. STFPM의 `timm.create_model` 치환(v0.1)도 동일한 성격의 위험을 이미 안고 있는, 기존에 받아들인 패턴이다.
- 처리: **수정 안 함.** 락 도입은 실사용 경로가 없는 위험에 비해 과한 복잡도라 판단했다. `UPSTREAM-INVENTORY.md` §12.2에 기록.

### Minor — DFM/DFKDE의 "1회 fit" 상태가 checkpoint resume에 보존되지 않음

- 위치: `adapters/dfm.py`, `adapters/dfkde.py`
- 지적: `_fitted`가 일반 Python bool이라 checkpoint에 저장되지 않는다. resume 후 새 adapter의 `_fitted=False`로 인해 다음 validation 직전 PCA/KDE가 재적합된다.
- 판정: **타당하나 신규 결함 아님.** PatchCore의 `_memory_bank_fitted`, PaDiM의 `_gaussian_fitted`와 동일한 기존 패턴.
- 처리: **수정 안 함.** `UPSTREAM-INVENTORY.md` §14에 기록.

### 항목별 확인 결과 (Codex 원문 요약)

SSOT 무결성(8개 복사본 모두 import 경로 치환만), Lightning 잔재 없음, 공통 engine 미오염, 학습/평가 데이터 누수 없음, DFKDE의 anomaly-map 부재 경로 안전성, CFA `.image` 데이터 브리지의 정확성, 등록 파일(`__init__.py` 2개)의 export-only 여부는 모두 "이상 없음"으로 확인됐다.

## 회차 1 이후 — 사용자 실행 중 발견된 결함 (Codex 미검출, 수정함)

Codex 검토를 통과한 뒤 사용자가 실제로 `python scripts/train.py ... --model configs/anomaly/models/cfa.yaml`을 bottle 카테고리로 실행했다. 두 가지 결함이 실행 중에만 드러났다 — 둘 다 정적 검토와 회차 1의 합성 배치 스모크(단일 스텝, `initialize_centroid`를 우회한 수동 `memory_bank` 세팅)가 놓친 것들이다.

### 실행 결함 1 — `radius: 1e-5`가 YAML에서 문자열로 파싱됨

- 증상: `build_cfa` 호출 시 `TypeError: only integer tensors of a single element can be converted to an index` (`torch_model.py:174`, `self.radius = torch.ones(1, requires_grad=True) * radius`).
- 원인: PyYAML은 소수점 없는 지수 표기(`1e-5`)를 YAML 1.1 스펙에 따라 float가 아니라 문자열 `'1e-5'`로 파싱한다 — 잘 알려진 PyYAML 함정. `configs/` 전체에서 이 패턴은 `cfa.yaml`의 `radius` 한 곳뿐이었다(다른 모든 config의 scientific notation은 이미 `1.0e-3`류 소수점 포함 표기였다).
- 처리: **수정 완료.** `configs/anomaly/models/cfa.yaml`의 `radius: 1e-5` → `radius: 1.0e-5`.

### 실행 결함 2 — `CfaLoss.radius`가 non-leaf 텐서를 스텝 간 공유해 두 번째 backward에서 실패

- 증상: 첫 스텝은 성공하고 두 번째 스텝의 `backward()`에서 `RuntimeError: Trying to backward through the graph a second time`.
- 원인: `loss.py:58`의 `self.radius = torch.ones(1, requires_grad=True) * radius`는 leaf가 아니라 `grad_fn`을 가진 non-leaf 텐서다. `CfaAdapter.__init__`이 `CfaLoss`를 한 번만 생성했으므로 모든 학습 스텝이 이 텐서 하나를 공유했고, 첫 `backward()`가 그 그래프를 해제했다. anomalib은 `Cfa.backward`를 `loss.backward(retain_graph=True)`로 오버라이드해 우회한다(`lightning_model.py:233`, "Investigate why retain_graph is needed"라는 TODO가 붙어 있다 — 이번에 그 원인을 규명했다). 이 프로젝트의 공통 engine에는 모델별 backward 훅이 없고, 전체 그래프를 매 스텝 유지하는 것은 메모리 누수로 이어진다.
- 처리: **수정 완료.** `CfaAdapter.train_step`이 매 스텝 `self.cfa_loss.radius`를 새 텐서로 재생성한다. `radius`는 `nn.Parameter`가 아니고 `build_optimizer`에도 전달되지 않으므로(CFA는 backbone을 freeze해 descriptor만 optimizer에 들어간다) 이전 스텝에 쌓였을 그레이디언트가 적용된 적이 없어 수치적으로 anomalib과 동일하다. SSOT 파일(`loss.py`)은 수정하지 않았다.
- 재검증: 4스텝 연속 `train_step`+`backward()`+`optimizer.step()`으로 재현 조건을 실제로 통과시키는 합성 테스트를 추가로 작성해 통과 확인. 이어서 사용자가 동일한 수정 코드로 bottle 학습을 다시 실행해 완주를 확인했다("잘 실행이 됩니다").

## 결론

Codex 회차 1에서 Critical 0건, Major 4건(1건 수정, 3건은 기존 6개 모델과 공유하는 설계라 이번 세션 범위 밖으로 판정), Minor 1건(기존 패턴, 미수정)을 확인했다. 회차 1 이후 사용자의 실제 학습 실행에서 Codex가 검출하지 못한 결함 2건(YAML 파싱, non-leaf 텐서 그래프 재사용)을 추가로 발견해 모두 수정했다. 실행 횟수는 1회만 소진했으며(한도 3회), 미해결 Critical은 없다.

**교훈**: 정적 검토와 단일 스텝 합성 스모크는 CFA처럼 상태를 스텝 간 유지하는 모델의 결함(회차 1 이후의 두 건 모두 "두 번째 이상의 스텝에서만" 드러난다)을 놓친다. 실제 데이터로 최소 2 스텝 이상 학습을 실행하는 것이 정적 검토를 대체할 수 없는 이유다.
