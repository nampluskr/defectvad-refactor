## 배경 — CFLOW 고유의 학습 구조

Upstream `lightning_model.py`는 `automatic_optimization=False`로 선언하고, 이미지 배치 하나마다 feature map을 `fiber_batch_size` 단위 조각("fiber")으로 잘라 각 fiber마다 독립적으로 `opt.zero_grad()`/`manual_backward()`/`opt.step()`을 호출한다(기본 config 기준 배치당 약 168회). 이 프로젝트의 공통 engine(`src/core/engine.py` `_train_epoch`)은 `adapter.train_step()` 호출 1회당 정확히 1회의 `zero_grad`+`backward`+`step`만 수행하므로, CFLOW의 학습 루프를 그대로 옮기려면 이 계약과 충돌한다.

## 회차 1 — 지적 및 처리

### Major 1 — optimizer-step 붕괴가 CFLOW 학습 역학을 실질적으로 바꿈

- 지적: 최초 구현은 모든 fiber의 loss를 합산해 배치당 평균 1개 loss를 만들고 engine이 1회만 backward+step 하도록 했다. 이는 upstream의 "fiber당 168회 Adam step"과 수학적으로 다른 최적화 스케줄이며, 수렴에 영향을 줄 수 있다.
- 판정: **타당함.**
- 처리: **수정 완료.** `CflowAdapter`가 `on_fit_start`에서 decoder 파라미터에 대한 전용 `torch.optim.Adam`(`self.decoder_optimizer`, `adapter.params.lr`로 설정)을 직접 만들고, `train_step` 내부에서 upstream과 동일한 순서로 fiber마다 `zero_grad()`/`loss.mean().backward()`/`step()`을 수행한다. engine에 반환하는 "loss"는 `0.0 * parameter`를 decoder 전체에 대해 합산한 더미 텐서로, 실제 학습에는 관여하지 않지만 `.backward()`가 성립하도록 decoder 그래프에 연결돼 있다. `build_optimizer`가 만드는 engine 소유 optimizer는 같은 decoder 파라미터를 대상으로 하지만 항상 정확히 0인 gradient만 보므로 Adam의 1차/2차 모멘트가 영원히 0으로 유지되어 step이 항상 no-op이 된다(회차 2에서 기본 config 조건 하에 수학적으로 재검증됨).
- 재검증: bottle 카테고리 1-epoch 스모크 재실행 결과 test image_auroc 0.908→1.000, pixel_auroc 0.927→0.987로 개선. `configs/anomaly/models/cflow.yaml`에 `adapter.params.lr: 0.0001`을 추가하고 `optim.optimizer`가 이 모델에는 구조적으로만 필요하고 실제로는 비활성임을 주석으로 남겼다.

### Major 2 — `weights_path=None`이면 조용히 random-init encoder 반환

- 지적: `build_cflow(weights_path=None)`이 에러 없이 학습되지 않은 encoder를 반환한다.
- 판정: **타당하나 신규 결함 아님.** `build_stfpm`(`stfpm/__init__.py:28`)과 `build_fastflow`(`fastflow/__init__.py:75`)도 동일하게 `if weights_path is not None:` 패턴만 있고 else 분기가 없다. 회차 2에서 정확한 사실 확인을 받았다.
- 처리: **수정 안 함.** 9개 모델 중 다수가 공유하는 기존 설계로, CFLOW 단독 회귀가 아니다. 표준 `cflow.yaml`은 항상 유효한 경로를 채워 넣으므로 CLI 정상 경로는 영향받지 않는다. 코드베이스 전역 이슈로 별도 과제 대상.

### Minor — fiber 크기가 나뉘어떨어지지 않을 때 upstream과 다른 가중치로 평균됨

- 지적: 최초 구현의 `total_loss / total_count`(원소 단위 평균)는 fiber 크기가 균일하지 않으면 upstream의 "fiber별 평균의 평균"과 다른 가중치를 준다. 기본 config(256×256, batch 8, wide_resnet50_2)는 세 레이어 모두 64로 나누어떨어져 영향이 없다.
- 판정: **Major 1 수정으로 무의미해짐.** fiber마다 독립적으로 `loss.mean().backward()`+`step()`을 수행하게 되어, 이 값은 이제 로깅 전용이며 실제 gradient/optimization에 전혀 관여하지 않는다.
- 처리: **수정 안 함 (moot).** best-checkpoint 선정 기준(`train.monitor.metric: image_auroc`)도 학습 loss가 아니므로 영향 없음.

## 회차 2 — Major 1 수정 검증 및 신규 발견

### Major (신규) — checkpoint resume 시 CFLOW의 실제 Adam 상태가 유실됨

- 지적: `CflowAdapter.on_fit_start()`가 매번 새 `decoder_optimizer`를 생성한다. `src/core/checkpoint.py#save_checkpoint`는 engine 소유(항상 비활성인) optimizer만 저장하고, `Engine.fit()`은 `adapter_state`를 채워 넣지 않으며, `CflowAdapter`는 `state_dict()`/`load_state_dict()`를 구현하지 않는다. `--resume`으로 이어서 학습하면 decoder 가중치와 RNG는 정상 복원되지만 Adam의 1차/2차 모멘트는 0부터 다시 시작해, 끊김 없이 학습한 경우와 달라진다.
- 판정: **타당함.**
- 처리: **수정 안 함 (범위 밖).** 해결하려면 `src/core/checkpoint.py`/`src/core/engine.py`에 adapter-state 체크포인트 훅을 추가하는 공통 코드 변경이 필요하다(`checkpoint.py`에 `adapter_state` 매개변수는 이미 존재하지만 `engine.py`가 채워 넣지 않는, 이번 세션 이전부터 있던 미완성 확장점이다). 단일 모델 포팅 범위(NFR-005)를 벗어나므로 별도 과제로 이월하고, `CflowAdapter` docstring에 "`--resume`은 decoder 모멘텀을 보존하지 않는다"는 제약을 명시했다.

### Minor — AMP/`train.grad_clip`이 CFLOW의 실제 업데이트에 영향을 주지 않음

- 지적: 실제 fiber별 backward+step은 engine의 `GradScaler`/`clip_grad_norm_` 시퀀스 바깥에서 일어나므로, `runtime.amp`나 `train.grad_clip`을 켜도 CFLOW의 진짜 decoder 업데이트에는 적용되지 않는다.
- 판정: **타당하나 기본 config(`amp: false`, `grad_clip: null`)에서는 영향 없음.** upstream 자체도 `trainer_arguments`로 `gradient_clip_val=0`(클리핑 없음)을 명시한다.
- 처리: **수정 안 함.** `CflowAdapter` docstring에 이 한계를 명시.

### Minor (신규) — `randperm`/`arange`가 CPU가 아닌 GPU RNG를 사용

- 지적: 최초 구현은 `torch.randperm(..., device=device)`로 fiber 순서를 생성했지만, upstream은 device를 지정하지 않아 CPU RNG를 사용한다. 알고리즘적으로는 동등하지만 동일 seed에서 upstream과 동일한 순열을 재현하지 못한다.
- 판정: **타당함.**
- 처리: **수정 완료.** `perm = torch.randperm(embedding_length).to(device)`로 변경해 무작위 샘플링 자체는 CPU RNG 스트림에서 이루어지도록 했다(인덱싱에 쓰이는 `torch.arange`는 결정적이라 RNG와 무관, 기존대로 `device=device` 유지).
- 재검증: bottle 카테고리 1-epoch 스모크 재실행, image_auroc=1.000·pixel_auroc=0.985로 회차 1 수정본과 동등한 성능 확인.

### 항목별 확인 결과 (회차 2 기준)

SSOT 무결성(3개 복사본 모두 import 경로 치환만), Lightning 잔재 없음, 공통 engine 미오염, lifecycle hook(별도 calibration 불필요, `on_fit_end` 상속으로 threshold 계산 정상), 오프라인 위반 없음(`pre_trained=False` 경로만 사용), frozen encoder(`TimmFeatureExtractor.forward()`가 `requires_grad=False`일 때 항상 내부적으로 `eval()`+`no_grad()`를 강제하므로 EfficientAD 방식의 instance-level `train()` 고정 불필요), weight-loading 정확성(경로 제공 시 정상, 누락 시 Major 2로 별도 기록)까지 모두 "이상 없음"으로 재확인됐다.

## 결론

Critical 0건. Major 2건 중 1건(optimizer-step 붕괴) 수정 완료·1건(weights_path 누락)은 코드베이스 전역 기존 패턴이라 반박. 회차 2에서 신규 Major 1건(checkpoint resume 시 Adam 모멘텀 유실)을 발견했으나 공통 engine 변경이 필요해 범위 밖으로 이월하고 docstring에 제약을 명시했다. Minor 2건 중 1건(RNG 기기 불일치) 수정, 1건(AMP/grad_clip 비적용)은 기본 config에서 무해해 문서화만 했다. 실행 횟수 2회 소진(한도 3회), 미해결 Critical 없음.
